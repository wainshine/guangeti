## 2. 本轮新发现

### P1 级

**2-1 [A] 发布说明与制品不符：ribbon 回退字修复未进入 v1.6.0 字体。**
代码已按正确口径修复，但发布链复用了 10-25 的 `work/generated.jsonl`（未重跑 10_generate/36）。RELEASE-v1.6.0.md 称「`10_generate`/`36_fill_fallback` …修掉回退字偏轻 ~15%」，实测发布字体中 1,833 个回退字仍按旧口径（0.714 ink/wk，与错误口径重放比值 0.998）。**改进**：发布流程加一步「生成文件时间戳必须晚于代码修改时间」的校验（B 的 64_package_b 新鲜度闸有这能力，A 没有）；或在发布说明中如实注明「代码已修，字形待重生成」。

**2-2 [A] 发布链质检仍无硬闸、无孔洞审计（13_qa.py 未动）。**
A 线 v1.6.0 发布时 13_qa 仍「只打印不中止」；且 A 没有任何孔洞检查——实测 A Regular 2.8% lost（含 `室 0/1`）、24.3% fewer、仅 24.8% 与文楷孔数一致。B 的 63_qa_b+71_holes_b 整套机制可直接复用（71_holes_b 的 --font 参数是通用的）。**改进**：A 的发布链接入 63_qa_b 式硬闸 + 71_holes_b 式孔洞审计，或直接让 13_qa 调用通用版本。

**2-3 [B] 孔洞闸设计缺陷：写的是「不许有 0 孔字」，代码只卡 lost≤8%，且完全不查 fewer。**
63_qa_b 文档串称「no glyph with 0 holes where WenKai has >= 1」（硬），代码实际 `lost/comparable > 0.08` 才失败；`fewer` 完全不计。发布字体实测 lost 5.6%（B-Real 含 `曰 0/1`、`悅 0/1` 这类常用字）、fewer 39.3%——按现行闸门**可以通过**。**改进**：把「lost 字清单」（尤其常用字白名单）纳入硬闸；fewer 设单独阈值（如 >15% 失败）；或把闸改成「lost 必须为 0」并在修复根因①前用 `--holes 0` 明确豁免 + 发布说明注明豁免理由。

**2-4 [B] 新 QA 闸未在最终发布链上执行。**
`work-b/log_qa.txt` mtime 11:05，而 B-Regular 13:15 重建、zip 13:47 打包——最终发布链没有重跑 63_qa_b（或其输出未落盘）。73_selfaudit 通过不能替代 63_qa_b（前者只查一致性、不查字形质量）。**改进**：发布链脚本加「QA 日志必须比字体新」的自检；或打包前强制重跑 63_qa_b 并断言退出码。

### P2 级

**2-5 [B] dewarp 闸未作用于发布数据。** 51_segment_b 的 `dewarp_fail` 字段已实现，但 `work-b/cells.jsonl` 是 10-25 切的数据（无该字段），发布字体仍包含 5 个超标叶的 cell。**改进**：下次重切时生效；短期可对 10-25 数据离线补算 dewarp 指标并标记。

**2-6 [A] 孔洞修复工具未启用且只覆盖真迹。** `07_build_real --carve-holes`（实验，默认关）只处理 A 真迹；A 的 GAN 合成字（`国` 类，孔环越出外框）无对应修复路径，B 的 `--close 7` 也只作用于 57 真迹路径，60_generate_b 的 GAN/回退路径无 close/carve 选项。**改进**：生成路径（10/60、36/61）加可选 closing；或按发布说明走 450–600 dpi 全链路重渲染。

**2-7 [A] 发布链各步之间无「输入新于字体」防呆。** 07 重出了真迹（13:30），但 11 用的 generated.jsonl 是 10-25 的——混合新旧输入出字体。这正是 2-1 的机制性根因。**改进**：把 B 的 64_package_b 新鲜度闸移植到 14_package，并在 11/62 构建时校验输入 mtime。

**2-8 [A] `四/目/自` 等掩膜融合字无修复计划落地。** 发布说明声明需 450–600 dpi 重渲染全链路重跑，但没有对应脚本/里程碑（`--carve-holes` 是 A 侧实验，B 用 `--close`，两者机制不同、效果未统一评估）。**改进**：把「高 dpi 重渲染」写成 PLAN 里程碑；先在两线各 50 常用带孔字上对比 carve/close/高 dpi 三种方案的孔恢复率与笔画增粗副作用。
