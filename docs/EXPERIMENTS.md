# 实验记录（可复现）

> 本文件记录本项目所有"生成 19,317 个缺字"的尝试、配置与客观指标。
> 指标统一为：**二值化 Dice**（预测墨迹 ∩ 真迹 / 并集×2），在留出字上计算；越高越好。
> 参考基线：**直接拿霞鹜文楷当输出 = 0.431**（即"什么都不做"的分数）。
>
> 指标口径（2026-10-23 起）：Dice 强烈奖励加粗，必须与“墨量比”同时报告；
> 早期只有 Dice 的结论已在下文用等墨量复测修正。评估集统一为 `work/eval_clean2.json`（91 字无泄漏）。

## 指标口径

```python
def dice(pred_mask, target_mask):
    a, b = pred_mask > 127, target_mask > 127   # 或 <128，取决于图片极性
    return 2 * (a & b).sum() / (a.sum() + b.sum())
```

留出集：`data/zi2zi_ds2/test.npz` 的 8 字（zi2zi 系列），或 `work/pairs/pairs.npz` 的
120 字验证集（自训 U-Net）。**注意：8 字样本太小，zi2zi 的 0.528 有 ±0.05 的波动。**

## E1 — 自训 U-Net v1（像素级风格迁移）

- 脚本：`scripts/09_train.py`（旧版）
- 数据：`work/pairs/pairs.npz`，2,185 组（霞鹜文楷 256² → 刻本裁剪 256²）
- 问题：目标来自灰度裁剪的二值化，**含印刷圈点、被截断的撇捺**；模型学到的是噪声
- 配置：U-Net base32 depth4，BatchNorm，残差连接，BCE + 0.5·L1 + 2·边缘梯度，80 epoch（实际到 ep16）
- 结果：val L1 0.202（"全零"基线 0.235，恒等 0.259）
- 目测：笔画发虚、粘连，阈值化后破碎
- 结论：**失败**。根因判断为训练目标脏 + 欠拟合。

## E2 — 自训 U-Net v2

- 脚本：`scripts/09_train.py`（2 通道版）
- 改进：输入加距离变换通道；GroupNorm 取代 BatchNorm；目标换成干净二值（但还是旧提取）
- 配置：256²，batch 16，lr 8e-4，45 epoch（1,171 s）
- 结果：val L1 0.210，best 0.2103
- 目测：仍是"鬼影"
- 结论：**失败**。此时意识到目标本身有问题（圈点/断笔），转向先修数据。

## E3 — 自训 U-Net v3（patch 训练 + Dice）

- 前置：v1.1 切字修复完成（黑圈点剔除、两遍归属、掩膜直出）
- 脚本：`scripts/09_train_b.py`
- 数据：1,675 组干净配对；128² 随机 patch；2 通道（raster + DT）
- 配置：U-Net base32，GroupNorm，BCE + Dice，batch 32，lr 3e-4，OneCycle，120 epoch（实际到 107）
- 结果：soft valDice 0.487（ep5 曾达 0.564，之后过拟合下降）；**二值化 Dice 0.441 vs 恒等 0.431**
  → **等墨量复测（2026-10-23）**：阈值 0.5 时墨量 1.247，Dice 0.441；阈值 0.6 时墨量 0.509、Dice 0.301。
  插值到墨量 1.0 时 Dice ≈ 0.37，**低于 ribbon 的 0.420**——当初的 0.441 是加粗换来的。
- 目测：结构对、笔画软；阈值化后缺口多
- 结论：**失败**（+0.010，无实用价值）。

## E4 — IDS 部件拼字

- 脚本：`scripts/ids_build.py`（解析器 + 12 个算子的排版引擎）
- 数据：`data/ids/ids.txt`（cjkvi-ids，88,937 条）
- 覆盖率（对 19,317 缺字）：
  - 完全可用真字拼出：**1,166（6.0%）**
  - 部分真字 + 基底部件：16,810（87.0%）
  - 无法分解：1,506（7.8%）
- 目测：`只` 的口过小、`企` 上部错位、`吉` 的口位置错；比例规则是瓶颈
- 结论：**不用于全量**。规则体系（约 120 条比例规则）是数天级工程，且 87% 混拼仍会风格打架。

## E5 — zi2zi-JiT 零样本

- 仓库：https://github.com/kaonashi-tyc/zi2zi-JiT （MIT，权重在作者 Google Drive）
- 权重：`data/models/zi2zi/zi2zi-JiT-B-16.pth`（2.1 GB）
- 数据构建：`data/vendor/zi2zi-JiT/scripts/generate_font_dataset.py`（用 `build/GuanGeKai-Real.ttf` 作为目标字体、思源宋体 Light 作为源字体）→ `data/zi2zi_ds2/`
- 推理：`generate_chars.py --device mps --num_sampling_steps 25`（cfg 2.6，heun）
- 结果（8 字）：**Dice 0.528**，基线 0.309（+71%）
  → **40 字复测：0.437 / 墨量 0.873 / 端帽 KS 0.283**（小样本高估，见 E14、REPORTS §3.5）
- 视觉：字重与笔锋明显接近刻本；但偏粗、偏匀
- 结构问题：400 字上有约 1/4 出现粘连/缺笔（孔洞数不一致）
- 结论：**目前最好的风格来源**，但必须加结构闸门。

## E6 — zi2zi-JiT LoRA 微调（第一轮）

- 脚本：`lora_single_gpu_finetune_jit.py`
- 配置：500 字、40 epoch、batch 16、LoRA r=32、0.28 s/it、总耗时 **5:52**
- 推理：cfg 2.6 → Dice **0.514**（低于零样本 0.528）
- 结论：**欠训**（仅 1,240 步）。建议用全部 1,675 字、20,000+ 步重跑（约 1.5 小时）。

## E9 — 墨量修正（v1.2.0，仅纵向腐蚀）

在 v1.2.0 的滤波字形上做**仅纵向**的形态学腐蚀，把字体级墨量从 1.26 压到 1.09。
横向不做，因为横向腐蚀会先吃掉竖画的宽度，字看起来"变瘦"而不是"变轻"。

后记：这条方案在 v1.3 被带状扫掠取代（E15），但"墨量是主矛盾"这个判断一直成立，
最终在 v1.3.4（按复杂度自适应 scale）与 v1.5.0（GAN + 阈值校准）里以更细的方式解决。

## E8 — 骨架 + 距离场笔刷引擎（2026-10-22）

- 代码：`scripts/brush_lib.py`（骨架、剪枝、笔画图、笔画帧、宽度模型、距离场渲染）
- 拟合：150 个真字、51,621 个骨架点；模型
  `r = r0·(1+k·vert^p)·(1+be·exp(-(d_free/le)²))·(1+bj·exp(-(dj/lj)²))`
- **2026-10-22 修正**：`stroke_edges` 曾把「端点（度 1）」误判为「交叉点（度 ≥3）」，
  导致 `d_free` 恒为 inf、端部模型从未真正生效。修正后重拟合，优化器选择 **be=0**
  （端部不需要额外加宽），RMSE 2.58 px。上一版「端部加宽 35%」的结论作废。
- 渲染：距离场零等值面（`render_field`），101 ms/字
- 结果（60 留出字）：

| 配置 | 墨量/真字 | Dice |
|---|---|---|
| 霞鹜文楷（恒等） | 1.20 | 0.445 |
| 距离场 scale 0.85 | **1.04** | 0.426 |
| 距离场 scale 0.90 | 1.10 | 0.434 |
| 距离场 scale 0.95 | 1.18 | 0.448 |

- **关键发现**：真字的墨量比霞鹜文楷**轻 20%**，竖横比为 1.19（文楷 1.08）。
  当前发布版（横膨2+纵蚀1）墨量 1.26、对比度 1.50，属于"在已偏重的基础上继续加粗"。
- **结论**：栅格层面的加粗/减细能匹配墨量与对比度，但**无法复刻刻刀的角状收笔**；
  距离场版在等墨量下与文楷观感接近，尚无可见的风格增益。
- 下一步候选：端部模板迁移（从真字裁 4 种朝向的收笔小块，贴到合成字端点）。

## E11 — 小字号可区分性与指标验证（2026-10-23）

### M0：端帽改动在实用字号下可见吗

用同一判别器（逻辑回归 + 低层特征，5 折 AUC）：

| 对照 | 16px | 24px | 32px | 48px |
|---|---|---|---|---|
| 真字（去噪）vs 合成 v1.2 | 0.939 | 0.972 | 0.983 | 0.973 |
| **合成 v1.2 vs 合成+E10 端帽模板** | 0.788 | **0.821** | 0.870 | 0.926 |

- 第一行：整体差异可分辨，但混入了扫描噪声，不能单独归因于笔锋。
- 第二行：**只改端帽**，其余完全相同 → 24px 下 AUC 0.82，说明端帽改动在正文尺寸可见。
- 结论：**M0 通过**，方案前提成立（但 E10 模板有毛刺，真实 v1.3 的可见度可能略低）。

### E12 — computer-grass / rhyme-grass 深挖（2026-10-23）

**读源码结论**（`grass.dh`，Dither 语言，315 行）：

| 机制 | 做法 | 对我们的可用性 |
|---|---|---|
| 骨架输入 | MakeMeAHanzi 的 `graph.hershey`，**逐点带 z（笔压/宽度）** | ❌ APL 许可，不可用 |
| 笔刷动力学 | 目标点追骨架，`vel += dir*l*ACCEL; pos += vel; vel *= DAMP` | 只影响**路径平滑**，不影响宽度 |
| `dip` | 每笔随机墨量：`z' = z^POW_Z * MUL_Z * (1+dip) + ADD_Z` | ✅ **可借鉴**：解释了我们测到的「同类型内端帽/笔宽方差极大」 |
| `needle` | 末笔竖画延长并收锋 | ✅ 可借鉴（出锋） |
| 飞白 | 填充带内随机断线 | ⚠️ 实测真字边缘粗糙度只比合成字高 3%（1.034 vs 1.004），不是主因 |
| 圆形顿笔 | 只在 `do_circ_cap=1`（草书配置）启用，**楷书配置是 0** | ❌ 楷书配置不用，我的对照实验也证明转角落点难检测 |
| 参数 | `regular.json`: `mul_z=0.04, add_z=-0.5, pow_z=1.75` | 其「楷书」是**刻意做细**的，与馆阁体的厚重相反 |

**rhyme-grass-font**（OFL 1.1，明《草韵辨体》）：

- 13,000+ 样本、**10,000+ 唯一字**、IDS 合成 4,500 字、异体字映射 3,000 字。
- 真正可借鉴的是**数据策略**：用「字典类刻本」而不是「一部书」作字源，能得到 10 倍于我们的真字量；
  以及 IDS 合成只用于「简单两部件、草书不连写」的字。
- 其字形数据许可干净（自有扫描），但其书是草书，不是我们的目标风格。

**结论**：这两个仓库的**渲染机制**我们已基本覆盖（宽度沿骨架、端部、飞白），
真正没吃到的只有 `dip`（逐笔宽度扰动）与 `needle`（出锋）；
而它们对我们最大的启示其实在**数据侧**——找「字典类楷书刻本」才能把 1,675 提到万级。

### E13 — 逐笔墨量扰动 `dip`（2026-10-23，成功）

从 computer-grass 的 `dip` 机制得到启发：每个笔画有独立的墨量（宽度）扰动。

**测量**（1,675 真字中抽 120 字）：

- 每个笔画的相对宽度（笔画中段中位数 / 该字全部笔画中位数）：
  **IQR 0.81–1.23、p10–p90 0.60–1.44、字内 CV 0.311**。
- 同一个字里，笔画粗细天然相差 ±20–40%，而合成字几乎是等宽的。

**实现**：`brush_lib.render_field(..., dips=[...])`，每个笔画从真字分布抽样一个宽度乘子，
再按均值归一（保证总墨量不漂移）。

**结果**（150 个留出字）：

| 方案 | 逐笔宽度 CV | KS vs 真字 | Dice |
|---|---|---|---|
| 真字 | 0.342 | — | — |
| v1.2.1 笔墨滤波 | 0.113 | 0.279 | 0.419 |
| **field + dip** | **0.370** | **0.029** | **0.423** |

- 这是目前唯一**同时改善风格统计与 Dice** 的方法。
- 全量生成：19,317 字约 8 分钟（12 进程），输出 329 MB（比滤波版大 44%），
  构建后字体 26 MB（v1.2.1 为 21 MB）。
- 视觉：`work/preview/v13_ab.png` 第二行（预览图已清理）；笔画粗细有了自然的起伏，
  但因为是独立抽样，笔画之间没有相关性，密集字会显得略“抖”。

**待定**：是否作为 v1.3.0 发布，需与 zi2zi LoRA 的结果对比后再定。

### E15 — 带状扫掠（ribbon）+ 斜切端头（2026-10-23，A 线采用）

### E17 — LoRA 输出的端帽优势能否在等墨量下保住？（2026-10-23）

**动机**：LoRA-40/600 的端帽 KS（0.054/0.093）是所有方案最好的，但墨量只有 0.67–0.70。
若把它加粗到 1.0 仍能保住端帽，就得到“LoRA 笔形 + 结构闸门”的组合。

**做法**：对 LoRA-600 的 40 个字，按字做**圆形结构元膨胀**，直到墨量达到真字水平（≈1.0）。

| 状态 | Dice | 墨量 | 端帽 KS | 笔内 std |
|---|---|---|---|---|
| LoRA-600 原始 | 0.396 | 0.673 | **0.093** | 0.258 |

**结论**：加粗确实把 Dice 抬到 0.485（超过 ribbon 的 0.420），但**端帽优势完全消失**（KS 0.093→0.267），

### E18 — ribbon 的机制层探索（2026-10-23）

在参数空间已饱和的前提下，试了三类“机制”改动（40 字无泄漏集）。

|---|---|---|---|

|---|---|---|---|---|
| 掩膜（未矢量化） | 0.420 | 1.077 | 0.101 | — |

| scale | alphamax | Dice | 墨量 | 端帽 cap_mid | 端帽 KS |
|---|---|---|---|---|---|
| 0.82（当前） | 1.0 | 0.433 | **1.159** | 0.622 | 0.187 |

### E21 — A 线的成绩有多少是内容字体的？（2026-10-23）

疑虑：A 线的指标可能主要来自霞鹜文楷，而文楷本身经过大量人工修饰，不能当作客观基准。

做法：同一个 `render_ribbon`，只换骨架来源（91 个没见过的字）。

| 内容字体 | 原样 Dice | ribbon 后 Dice | 原样端帽 KS | ribbon 后 KS |
|---|---|---|---|---|
| 霞鹜文楷（楷） | 0.435 | 0.416（−0.019） | 0.151 | **0.068（−55%）** |
| 思源宋体（宋） | 0.327 | 0.313（−0.014） | 0.115 | 0.103（−10%） |

**结论**：
1. **Dice 的绝对水平由内容字体决定**：换骨架后差 0.11（0.435 vs 0.327），
   而我们的渲染器对 Dice 的影响恒定在 −0.015 左右（两种骨架都一样）。
2. **我们的真实贡献在端帽与笔内变化**，不是 Dice。文楷上增益大（−55%），
   因为文楷端帽本来就钝（0.151）；思源宋体本来就近（0.115），可改空间小（−10%）。
3. 因此"A 线 Dice 0.432"应表述为"**在文楷骨架上的 Dice**"，
   不能说成渲染器的功劳；文楷还是一个人工修饰过的字体，它的 0.435 本身就是手调出来的基准。

### E22 — miter join 修转折（2026-10-24，未发布）

**动机**：`render_ribbon` 在每个骨架点盖圆盘，横折的外角必然是圆弧。审计建议改用 miter join：
两条偏移线求交，外角自然成方、内角自然成圆，且不像 `corner_boost` 那样靠盖方块假装。

**实现**：在 `render_ribbon` 加 `miter` 参数（默认 0，不影响现有产物）。对每个骨架点，取前后
约 2.5 倍半径的弦，若两弦夹角落在 45–120°，就把两条偏移线的交点作为楔形尖端填充。

**实测**（256px，口/日/乃）：

| 字 | 关闭 | 开启(1.8) | 增加 |
|---|---|---|---|
| 口 | 8,915 | 9,388 | +5.3% |
| 日 | 11,064 | 11,456 | +3.5% |
| 乃 | 9,810 | 11,219 | **+14.3%** |

**结论**：
- 直角转折（口、日）增量 3–5%，接近真迹的转角缺墨量（复现值 5.9–15.7%），方向对；
- 但尖锐转折（乃的钩）被填成一块，增量 14%，肉眼可见变脏；
- 根因是转角检测仍基于骨架曲率，无法区分「横折的直角」和「钩的锐角回头」。
  审计也指出 `20_corner_knock.py` 的 `turn_sites` 对三笔交汇的转折检测为零。

**下一步**：需要更好的转角判据（例如以真迹的转角位置为监督，或要求两条偏移线夹角在
70–110° 且转折前后的笔画方向与 IDS 结构吻合），而不是纯曲率阈值。代码保留（`miter=0` 默认关闭）。

|---|---|---|---|---|---|
| R0 连通域+字碗全等（**现行发布代码**） | 0.455 | 79 | 0 | **78** | 123/150 |
| R0b 仅字碗全等 | 0.513 | 58 | 0 | 57 | 75/150 |
| R1 字碗差 ≤1 | 0.585 | 30 | 1 | 30 | 39/150 |
| R2 连通域全等 | 0.481 | 70 | 0 | 69 | 110/150 |
| R4 IoU(GAN,文楷) ≥0.55 | 0.417 | 91 | 0 | 90 | 122/150 |
| R7 墨量比 ∈[0.7,1.3] | **0.651** | 9 | 0 | 8 | 20/150 |
| （参照）纯 GAN / 纯 ribbon | 0.675 / 0.417 | — | — | — | 76/150 / 145/150 |

**四个结论**：

1. **现行闸门几乎全错**：79 个字里 78 个是误回退，B 类 Dice 从 0.675 掉到 0.455。
2. **IoU 判据不可用**：GAN 输出与文楷的 IoU 中位只有 0.245——风格化本身就改变了形状，
   这不是偏移（按 bbox 对齐后也只到 0.282）。任何"与文楷重合度"类判据都会全军覆没。
3. **墨量判据最接近无损**（Dice 0.651，只退 9 个），但它几乎不保护结构（C 类拓扑 20/150）。
4. **没有判据同时满足"保住风格"和"保住结构"**。这是判据本身的局限，不是阈值没调好。

**指标口径警告**：C 类拓扑有两套定义，数字差很多——
只看字碗数：ribbon 145/150、GAN 76/150；同时看连通域+字碗：ribbon 122/150、GAN 17/150。
`26_bench` 的 `hole_agree` 列是**只看字碗**，引用时必须说明。

**决定**：不发布闸门混合方案。下一步不是继续找判据，而是提升模型本身
（K=4→8/12 扩容，数据目前只用了 11%），让"结构错"的比例从源头下降。

### E25 — 干净集重测：多实例到底有没有更好（2026-10-24）

**问题**：E23 的"未见字 0.552 → 0.675"被 B 类的定义骗了。`bench_unseen` 是相对**旧单实例划分**
定义的（旧模型按对切、120 对 = 120 字，91 个 B 类字恰好全在验证侧，0 泄漏）；
多实例版沿用同一套按对划分，5,833 对覆盖了**全部 1,675 字**，所以 B 类 91/91 全在训练集里。

**干净集**：`work/pairs_single.npz` 的 617 个字在书中只出现一次，从未进入任何训练。
脚本 `scripts/32_eval_clean.py`（n=300，seed 0），结果落盘 `work/eval_single.json`。

| 方法 | Dice | 墨量 |
|---|---|---|
| 霞鹜文楷原样 | 0.436 | 1.182 |
| ribbon v1.3.5 | 0.414 | 1.043 |
| **旧 ep150**（单实例 + 全局 D，150 轮） | **0.526** | 0.967 |
| 多实例 ep40（+ PatchGAN，40 轮） | 0.502 | 0.945 |

**结论**：

1. **多实例版在干净集上比旧单实例版低 0.024**，E23 的"提升泛化"是泄漏造成的假象。
2. 旧 ep150 在两个独立集合上互相印证（B 类 0.552 / 干净集 0.526），可信。
3. 但**这不是判死刑**：多实例与 PatchGAN 两个变量捆在一起改，且只训 40 轮（旧版 150 轮）。
   要归因至少需要三组对照：多实例+全局D、单实例+PatchGAN、多实例续训到 80 轮。
4. **评估口径从此改为**：任何"泛化"结论必须在 617 干净集上给出；
   `26_bench` 现在会打印每个类的「训练集覆盖」行，覆盖率高时该行不可用作泛化证据。

**"再训久一点会不会更好"——不会。** 用 617 干净集（n=150）逐快照评估多实例模型：

| epoch | 5 | 10 | 15 | 20 | 25 | 30 | 35 | 40 |
|---|---|---|---|---|---|---|---|---|
| Dice | 0.495 | **0.520** | 0.519 | 0.511 | 0.504 | 0.502 | 0.509 | 0.499 |

第 10 轮见顶（0.520）后缓慢下滑，40 轮是 0.499。对照旧单实例 ep150 的 0.526。
**欠训假设不成立**，续训只会更差——这一项不用再花 6 小时重跑。

### E26 — 归因四格：多实例还是 PatchGAN 的锅（2026-10-24）

E25 之后仍有两个变量捆在一起。本实验把它们拆开，各训 20 轮，用同一 617 干净集（n=150）评估。

| epoch | multi+PatchGAN | multi+全局D | **single+PatchGAN** |
|---|---|---|---|
| 5 | 0.495 | 0.475 | **0.516** |
| 10 | 0.520 | 0.509 | **0.541** |
| 15 | 0.519 | 0.525 | **0.543** |
| 20 | 0.511 | 0.523 | 0.526 |
| 25–40 | 0.504→0.499 | — | — |
| 旧 ep150 参照 | | **0.526** | |

（20 轮的成本：单实例 153 秒/轮，多实例 550 秒/轮。）

**结论**：

1. **多实例是拖累。** 无论配全局 D（0.523）还是 PatchGAN（峰值 0.520），都低于单实例+PatchGAN（0.543）。
   每字 4 个样本把输出推向它们的均值，泛化反而下降——E23 的"提升"确实只是泄漏。
2. **PatchGAN 有正收益。** 在单实例上，它把峰值从 0.526（旧全局 D，150 轮）提到 **0.543**（仅 15 轮），
   而且训练快 3.6 倍（153 vs 550 秒/轮）。
3. **最佳配置 = 单实例 + PatchGAN + 约 15 轮。** 20 轮已开始回落（0.526），说明 15 轮前后见顶。
4. 下一步若要重训发布候选，用这个配置；多实例的 5,833 对数据与已经跑过的 6 小时可以归档。

### E27 — 发布候选评估：GAN 最优配置能否替掉 ribbon（2026-10-24）

E26 的最优配置是「单实例 + PatchGAN + 15 轮」。用它做发布候选，在 617 干净集（n=150）上比较：

| 方案 | Dice | 拓扑一致（vs 文楷，连通域+字碗） |
|---|---|---|
| ribbon（v1.3.5 现行） | 0.418 | 87/150 |
| **GAN 原样** | **0.543** | **23/150** |
| GAN + 拓扑闸门 | 0.442 | 94/150 |

**解读**：

1. **GAN 原样不能用于发布**：Dice 高 0.125，但拓扑从 87/150 掉到 23/150——字碗画错、笔画断裂，
   对一个字体来说是硬伤，不是风格差异。
2. **闸门能救回结构，但只肯信 23/150 的字**（其余 127 个回退 ribbon）。
   净收益是 Dice +0.024、拓扑 +7/150——**相当于退回 ribbon，只换了 15% 的字**。
3. 所以 B 线到此为止：**在当前模型质量下，GAN 无法替代 ribbon，也不值得为 +0.024 引入一个 390MB 检查点。**

**B 线的结论汇总**（E23→E27）：多实例是错的（泄漏掩盖）；PatchGAN 是对的（+0.017）；但整体仍达不到
「可以整批替换 ribbon」的水平。真正的瓶颈不在判别器或数据量，而在**模型没有结构先验**——
它不知道「这个字该有几个字碗」。这也是 E24 的闸门为什么会失败：闸门和模型各自都不知道结构，
只能拿文楷当拐杖，而文楷自己有 53% 的结构与刻本不同。

**下一步只有两条**：① 换数据源（楷书字典刻本，把真字从 1,675 提到万级）；
② 给模型注入结构先验（部件分解 + 装配），不是继续调 GAN。

### E28 — 结构口径修正与横画倾角实验（2026-10-24）

**问题**：E24/E27 用「拓扑（连通域+字碗）等于**文楷**」当结构标准。但 A 线合成字的骨架就取自文楷，
这把尺子对 ribbon 是自动加分；而馆阁体与现代电脑楷体的结构本来就不同。

**实测一：换真迹参照，三者没有区别**（617 干净集同一批 150 字）：

| 参照 | ribbon | GAN | 文楷自己 |
|---|---|---|---|
| vs 文楷（旧口径） | 87/150 | 23/150 | — |
| **vs 真迹** | **17/150** | **16/150** | **17/150** |

连人工精修的文楷与刻本真迹也只有 17/150 全等。**这个指标全员 ~11%，测的是"像不像文楷"，不是结构对错。**
E24 的九判据全军覆没、E27 的 "GAN 结构崩坏"，都有一部分是这把尺子的锅。
**决定：结构评估不再使用「与文楷拓扑全等」。**

**实测二：维度化指标**（`scripts/33_struct_metrics.py`，120 字，参照真迹）：

| 维度 | 文楷 | 真迹 |
|---|---|---|
| 重心偏移 dx / dy | +0.001 / +0.026 | +0.009 / +0.029 |
| 宽高比 | 1.021 | 1.016 |
| 横画角（带符号中位） | −2.3° | −9.0° |
| 横画角 KS（文楷 vs 真迹） | **0.513** | — |
| 字碗数相等（文楷 vs 真迹） | **39/120** | — |

布局维度（重心、宽高比）几乎一致；**差异集中在笔画级**：横画更斜、字碗只有 1/3 对得上。

**实测三：横画倾角校准——无收益（证伪）**

把骨架里近水平的笔画绕自身重心旋转 Δ，再正常渲染，在 60 字上看 Dice：

| Δ | 0° | ±3° | ±6° | ±9° |
|---|---|---|---|---|
| Dice | 0.420 | 0.419–0.420 | 0.419 | 0.415 |

单字看也无一致收益（二 +3° 微升 0.033，一/三 下降）。原因有两个：
① 256px 上的 Hough 倾角估计本身不稳（用已知旋转校验：真值 −10° 估成 +5.4°）；
② 绕笔画重心旋转会同时移动笔画两端，破坏它与其余笔画的接续关系。

**结论**：**「结构校准」需要先有一个可验证的结构度量，而目前没有。**
在做出可靠度量（例如笔画级关键点配准、或部件级分割）之前，不要基于倾角这类人口统计量做形变干预。

### E29 — 分级结构度量：E27 的结论反转（2026-10-24）

E27 用「与文楷拓扑全等」判定 GAN 结构崩坏（23/150），E28 已证明那把尺子对 A 线循环、
对真迹无区分度。本实验改用**以真迹为参照的分级骨架度量**（`scripts/34_struct_score.py`）：

- `skel_chamfer_px`：两字形骨架之间的平均距离（双向），对齐质心后计算；
- `end_delta` / `junc_delta`：自由端点、笔画交叉点的数量差（按连通域聚类，不按像素）；
- `len_ratio`：骨架总长比。

**结果（617 干净集，n=100，参照全部是真迹）**：

| 方法 | chamfer(px) | 端点差 | 交叉点差 | 长度比 | Dice |
|---|---|---|---|---|---|
| 霞鹜文楷 | 8.78 | 4.5 | 16.0 | 1.025 | 0.455 |
| ribbon | 8.76 | 3.0 | 13.0 | 1.094 | 0.423 |
| **GAN ep15** | **6.68** | 4.0 | **9.0** | 0.841 | **0.591** |

**崩坏率（n=300，Dice < 0.30 视为崩坏）**：

| 方法 | 均值 | p5 | 最低 | 崩坏率 |
|---|---|---|---|---|
| ribbon | 0.413 | 0.293 | 0.219 | **5.7%** |
| GAN ep15 | **0.540** | **0.386** | 0.217 | **0.7%** |

**结论**：

1. **E27 的"GAN 结构崩坏"是循环指标造成的误判。** 用真迹参照的分级度量，
   GAN 在 Dice、骨架 chamfer、交叉点差三项上都优于 ribbon，崩坏率低 8 倍。
2. 视觉复核（8 个未见字，文楷输入 / GAN 输出 / 真迹三行）与指标一致：GAN 更厚重、有笔锋，
   更接近刻本；未见融合或断笔。
3. **B 线不该被"收束"。** 之前否掉它，依据的是一个会自动奖励 ribbon 的指标。
4. 仍需谨慎的部分：GAN 的骨架长度比 0.841（偏细长）、样本只有 300 字，
   且**尚未做过全量生成与字体级验收**。下一步应当生成全量候选字体再评，而不是继续在 91/150 的小样本上争论。

### E30 — M0：推理阈值扫描与崩坏率落盘（2026-10-24）

**目的**：GAN 的骨架长度比只有 0.84（比真迹短 16%），先试最便宜的修法——移动二值化阈值。

脚本 `scripts/35_threshold_sweep.py`，150 个干净字，阈值 −0.15…+0.05（步长 0.025）：

| 阈值 | Dice | 墨量 | len_ratio | chamfer | 端帽 KS |
|---|---|---|---|---|---|
| −0.150 | 0.546 | 1.047 | 0.835 | 6.39 | 0.158 |
| −0.075 | 0.544 | 1.036 | 0.831 | 6.40 | 0.159 |
| 0（现状） | 0.542 | 1.024 | 0.829 | 6.48 | 0.152 |
| +0.050 | 0.541 | 1.017 | 0.828 | 6.55 | 0.153 |

**结论（走 M0 的失败分支）**：

1. **len_ratio 对阈值完全不敏感**（0.826–0.835 全程不动）——说明偏短不是"判定偏保守"，
   而是**笔画端部本身被模型画短了**（收笔过尖/端部回缩）。阈值这条路修不了，按计划留给 M2。
2. 端帽 KS 全程 0.15 左右，比 ribbon 的 0.09 差——这也印证端部形状是弱点。
3. 崩坏率（Dice<0.30，n=150）已落盘 `work/failure_rates.json`：
   **ribbon 4.67%，GAN 0.67%**，与之前 n=300 的口头数字一致。

**下一步**：M1（目标图去模糊，训练与评估同口径）。

### E31 — M1：训练目标去模糊（2026-10-24）

**先纠正一个前提**：计划里写"评估集也是 σ=1.0 模糊"，实测不成立。

| 数据 | 中间灰度占比 | 说明 |
|---|---|---|
| 训练目标 `pairs_blur10.npz` | 9.06% | 二值掩膜 + 仿射 + `GaussianBlur(σ=1.0)` |
| 训练目标 `pairs_blur05.npz` | 5.12% | 同上，σ=0.5 |
| 评估参照 `pairs_single.npz` | **2.74%** | `24_build_singles.py` **没有做高斯模糊**，只有仿射插值 |

所以真实情况是**训练目标比评估参照更糊**——修正方向正确（让训练更锐，靠近评估），
但不存在"评估集要同步去模糊"这回事。原计划的 P1 修法基于错误假设，已改。

实验配置：σ=1.0（基线）vs σ=0.5（实验），其余完全相同（单实例 + 4 层 PatchGAN，15 轮）。
评估一律用未模糊的 `pairs_single.npz`（n=150，seed 7）。

| 检查点 | Dice | chamfer | len_ratio |
|---|---|---|---|
| 基线 σ=1.0 ep15 | **0.542** | **6.53** | 0.823 |
| σ=0.5 ep05 | **0.558** | 7.53 | 0.787 |
| σ=0.5 ep10 | 0.516 | 6.81 | 0.851 |
| σ=0.5 ep15 | 0.523 | 6.88 | **0.891** |

**结论：M1 判为「不通过」，按计划归档**：

- 去模糊确实改善了 M0 修不动的 **len_ratio**（0.823 → 0.891，向 1.0 靠了）；
- 但同时 **chamfer 从 6.53 升到 6.88**（骨架整体对不齐），Dice 也掉到 0.523；
- 曲线不稳：ep5 的 Dice 最好（0.558）但 chamfer 最差（7.53），说明是在两个指标间抖动，不是稳定改善。

净效果是"笔画更长、但整体更歪"，不满足 M1 的通过条件（chamfer 不劣于 6.68）。
**M2 仍用 σ=1.0 作对照**，去模糊留作后续变量（若 M2 的 80 轮稳定后再试）。

### E32 — M2：5 层 hinge 判别器 + 数据增强（2026-10-24/25）

**动机**：E26 的曲线在 ep15 见顶后回落（过拟合），而项目至今零数据增强。
M2 一次改三处：PatchGAN 4 层 → 5 层（感受野 ~70px）、BCE → hinge、加几何增强
（±2° 旋转、±3px 平移、0.95–1.05 缩放，X/Y 同步）。

**配置**：单实例 1,634 对，batch 16，80 轮，每轮 152–157 秒（共 3.5 小时），每 5 轮存快照。

**训练内 valDice（41 个按字留出的字）**：

| epoch | 5 | 20 | 40 | 60 | 80 |
|---|---|---|---|---|---|
| valDice | 0.518 | 0.556 | 0.581 | 0.592 | **0.619** |

**到 ep80 仍在上升**——与 E26「ep15 见顶」完全不同，说明增强确实把过拟合推后了。

**干净集（617 字，n=150，seed 7，参照真迹）**。Dice 列是**均值**（同一批字的中位是 0.599，
两个口径差 0.05，引用时须注明）：

| 检查点 | Dice | chamfer(px) | len_ratio |
|---|---|---|---|
| 基线 ep15（4 层 BCE 无增强） | 0.542 | 6.53 | 0.823 |
| M2 ep15 | 0.518 | 6.63 | 0.888 |
| M2 ep30 | 0.535 | 6.27 | 0.860 |
| M2 ep40 | 0.548 | 6.03 | 0.874 |
| M2 ep60 | 0.538 | 6.18 | 0.864 |
| **M2 ep80** | **0.549** | **5.92** | 0.886 |

**结论**：

1. **骨架 chamfer 降到 5.92，进入真迹样本间方差的同一量级**，但**没有打平**。
   同口径（seed 7）重测：GAN 5.92 [5.14, 7.27] vs 真迹互比 **5.16** [4.27, 6.65]，
   **KS p<0.001、Mann-Whitney 单侧 p=0.0001**，中位差 0.77px（15%）。
   （E29 的 5.88 是 n=120/seed 0/高频字的另一次抽样，与 5.92 不可直接相减——
   跨抽样比中位数是错误口径，本条已改。）
2. Dice 0.542 → 0.549（小幅），len_ratio 0.823 → 0.886（向 1.0 靠近）。
3. 三项指标同向改善，且没有牺牲任何一项——这在此前所有 GAN 实验里是第一次。
4. **增强是关键**：没有它，80 轮只会训到过拟合更深；有了它，valDice 到 ep80 还在涨。

**下一步**：M3（全量生成 + 字体级验收）。另一个选项是继续训到 120–150 轮看是否还能涨，
但边际收益需要和 M3 的收益权衡——先做 M3，因为它决定这个模型能不能用。

### E33 — M3：全量生成与字体级验收（2026-10-25）

**生成配置**：`--method gan`（新守卫：空 / 墨量 [0.6,1.5] / 连通域差 ≤3 → 回退 ribbon），
阈值 −0.05，512 渲染 + 轮廓简化 2.0，20,992 字全量。

**生成结果**：17,484 字走 GAN（90.5%），**1,833 字回退 ribbon（9.5%）**。回退字偏向复杂字
（平均墨量 13,695 vs GAN 字的 12,479）——笔画越多越容易触发守卫。

**字体级验收（全部针对成品 `build/GuanGeKai-Regular.ttf`）**：

| 项 | 结果 | 判定 |
|---|---|---|
| 覆盖率 | 20,992 / 20,992，空字形 0 | 通过 |
| 真迹子集 | 1,675 字形、1,675 cmap | 通过 |
| 字面位置一致性 | 真迹 (0.4987, 0.5218) vs 合成 (0.5014, 0.5213)，Δx 0.55%、Δy 0.11% em | 通过（阈值 <1%） |

### E34 — 小字号字重：三种口径（2026-10-25）

**背景**：v1.5.0 的发布说明写「12–14px 偏重 12–20%，16px 起基本持平」。审计复核后对这条提出质疑，
本实验用三种互相独立的测法判定。

脚本 `scripts/37_smallsize_e34.py` → `work/e34_smallsize.json`（120 真迹字 vs 120 合成字，seed 0）。

| 字号 | A 同字掉墨率（真迹/合成） | B 合成/真迹（中位数之比） | C 相对文楷（真迹/合成） |
|---|---|---|---|
| 12px | 0.016 / 0.015 | **1.161** | 0.750 / 0.833 |
| 14px | 0.021 / 0.021 | **1.195** | 0.794 / 0.896 |
| 16px | 0.027 / 0.028 | **1.178** | 0.818 / 0.893 |
| 20px | 0.043 / 0.043 | **1.157** | 0.865 / 0.940 |
| 32px | 0.110 / 0.111 | **1.173** | 0.837 / 0.919 |
| 96px | 1.000 / 1.000 | **1.158** | 0.842 / 0.929 |

**结论**：

1. **不存在"字号效应"**。A 口径（同字自比，字号 S 与 96px 的墨量比）两组在每个字号上几乎相同
   （12px 0.016 vs 0.015），说明**缩小时掉墨的比例一致**。
2. **合成字恒定比真迹重约 17%**，从 12px 到 96px 都是（B 口径 1.16–1.20），
   相对文楷则是约 1.10 倍。这是**固有墨量差**，不是小字号特有现象。
3. **v1.5.0 的披露是错的**，错在统计口径：当时用「两组独立样本的比值数组逐元素相除再取中位」——
   两个数组本不相配，这种算法没有意义，才产生出「12px 1.20 → 20px 1.00」的假收敛。
   正确做法是比值的中位数（B）或同字自比（A）。

**后续**：既然是**恒定**偏差，就可以用一次全局标定修掉（合成字整体乘 ~0.85）。
这比"披露"更对症，列入 v1.5.1。
