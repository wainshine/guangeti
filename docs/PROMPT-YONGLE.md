#### 2.1 朱丝栏是红的，可以直接做颜色分离

实测一页：红色像素占 4.4%，`r−g` 最大 **101**。

这是**巨大的利好**。A 线的源 PDF 也是彩色的（`r−g` 最大约 103），`red_mask()` 一直在跑，

**注意**：早期文档里"A 线源图被去色"的说法是错的，那是在流水线输出的灰度 PNG 上误测的。
**C 线红像素占 4.4%（朱丝栏 + 句读），收益是数量级差别**。可以直接做颜色分离：

- 朱丝栏（行线、边框）→ 红色掩膜，**直接删掉**，顺带得到精确的分栏结构；
- 红色句读圈点 → 同样是红通道，一并剔除；

`scripts/pageproc.py` 里已有 `red_mask()`，A 线在跑（只是四书红色标记太少、收益接近 0），**C 线是它第一个真正发挥作用的场景**。

#### 4.1 标签体系总览（纯 OCR 分支）

```
PDF → 红线分栏 → 切字 → PP-OCRv6（竖排）
    → 视觉聚类（同簇必须 OCR 一致）
    → 第二见证（换引擎/换预处理）
    → 引文校正（能匹配上的段落）
    → silver 标签（多见证且一致）→ 训练集
    → 干净集：按【页】留出，只用留出页上的多见证字
```

#### 4.2 OCR 是第一手来源

A/B 两线用的是 **PP-OCRv6 @ 150 dpi**。C 线要调整：

| 项 | 建议 |
|---|---|
| 渲染 dpi | **150**（与 A/B 一致，OCR 模型在该尺度上验证过；300 dpi 图先降采样） |
| 方向 | 竖排、从右到左 —— B 线已验证 `52_ocr_b.py` 的竖排模式可用 |
| 分栏 | **不要用 OCR 的框分栏**，用朱丝栏的红线分栏（更准，见 2.1） |
| 预处理 | 先剔红（栏线 + 句读），再 OCR，避免红线干扰 |
| 预期准确率 | **未知，必须先测**（见 4.5） |

#### 4.3 多见证：没有参照文本时怎么判标签可信

A/B 用"页级对齐率"当标签质量闸，C 线要换成**多重自证**：

```
一个字有 ≥2 次出现，且 OCR 全部一致 → 可信（silver）
只有 1 次出现                        → 存疑，只用于测试集，不进训练
同一位置 OCR 两次（不同尺度/不同预处理）不一致 → 丢弃
```

具体做法：

1. 全量 OCR，得到每格的 `label` + `score`（PP-OCR 的置信度）；
2. 同一字形的**视觉聚类**（对掩膜做归一化后的相似度聚类；**按 OCR 标签分组做，不做全局两两**，
   见 §11）——同簇的格子 OCR 必须一致，
   不一致的整簇丢弃。这一步能同时抓出 OCR 错和字形变体；
3. 统计每字的样本数，`n≥3 且全一致` 才进训练集。

**注意：自一致性 ≠ 独立见证。** 同一个 OCR 引擎对同一个字形会**一致地**读错
（`曰→日`、`己→已`、`刺→剌`、`王→玉`），错得越多越"可信"——这是闸门全绿、标签全错的组合。
所以必须补**第二种独立见证**（至少选两项）：

- 换引擎（PP-OCRv3 与 v6 交叉，或换 PaddleOCR-VL / DeepSeek-OCR 这类 VLM；见 §4.3b；PaddleOCR 与 PaddleOCR-VL 均为 Apache-2.0）；
- 换预处理（去红前/后各 OCR 一遍，或不同二值化）；
- 上下文合理性（引文来源的 n-gram、Unihan 常用度，剔除"读不通"的标签）；
- **形近字混淆对定向抽检**：`曰/日`、`己/已/巳`、`刺/剌`、`王/玉`、`戊/戌/戍`、`未/末`。

**§4.4 的引文校正由此从「可选」升为「必做」**——它是唯一能提供外部真理的路子。

#### 4.3b 第二见证用哪个引擎：先做三引擎对照（半天）

「换更强的 OCR」在 C 线**不是最大的杠杆**。版面能力（阅读顺序、表格、公式）对我们的价值接近零，
因为朱丝栏已经把分栏结构给死了。真正需要的是**错误模式不相关**的第二见证。

三类引擎的分工：

| 类别 | 代表 | 在本任务里的位置 |
|---|---|---|
| 经典检测+识别 | **PP-OCRv6**（A/B 线已在用） | **主引擎**。轻、快、可并行、输出框和字 |
| 文档理解大模型 | **PaddleOCR-VL（0.9B）**、**DeepSeek-OCR（约 3B）** | **候选第二见证**，不替代主引擎 |

**VLM 有两个特性对我们是毒药，必须知道：**

1. **会按上下文补全**——破损处能"猜"出通顺的字，但我们要的是**这个抄手写的那个字形**，
   猜出来的标签会污染真迹集；
2. **会规范化异体字**（`爲→为`、俗字→正字），而大典的价值恰恰在于俗字异体极多。

**但它的错误模式与经典 OCR 不相关**，这正是独立见证要的东西。用法：

| 用途 | 规模 | 说明 |
|---|---|---|
| silver 集抽检 | 1–2 万格 | 两引擎不一致的格子人工裁决，比纯人工快 5–10 倍 |
| 难例复核 | 破损 / 双行注 / 篆隶邻接 | VLM 的鲁棒性在这里真有优势 |
| **不做** | 70 万格全量 | 跑不动，也没必要 |

**验证协议（别凭印象选，半天做完）**：

```
样本：300 格 = 150 常规 + 50 形近字对（曰/日、己/已/刺/剌）+ 50 破损/污渍 + 50 双行注
引擎：PP-OCRv6 / PaddleOCR-VL / DeepSeek-OCR
指标：两两一致率 · 与人工核对的一致率 · 错误类型分布
      （形近混淆 / 异体规范化 / 幻觉补全 / 漏行）
```

**判据**：只有当某个引擎"与 PP-OCRv6 的错误不相关 **且** 绝对准确率更高"时，才值得当第二见证。
如果它只是"更会排版"，对 C 线没有价值。

**两个注意**：

1. **许可证**：PaddleOCR 与 **PaddleOCR-VL 均为 Apache-2.0**（已核实，可放心用）；
   **DeepSeek-OCR 条款未核实**，下载时看模型卡，别凭印象写进 `docs/DATA-C.md`；
2. **别抄网上的分数**——社区帖（CSDN/小红书）里的榜单与实测只能当线索。转述一句：社区提到
   PaddleOCR-VL 在 OmniDocBench V1.5 拿 92.6，但那张榜考的是版面/表格/公式，**不是单字标签准确率**。

#### 4.4 用引文校正 OCR（**必做**，唯一的外部真理来源）

《永乐大典》是类书，正文大量整段引用古籍。若能在公版古籍库（ctext、维基文库）里
找到同一段文字，就能反向校正 OCR：

```
OCR 文本 ──片段匹配──> 公版古籍中的同文段落 ──对齐──> 逐字校正
```

命中率未知（估 20–40%），但**命中的部分标签质量会接近 A/B 水平**。
**这是主路径之一**：凡能匹配上的段落，一律用引文校正后的标签；匹配不上的才退回纯 OCR 标签。

#### 4.5 开工前必做的三件探针（各 1 小时）

按顺序做，任何一件不达标就调整方案，别硬推：

1. **红通道探针**：随机 30 页，统计红线覆盖率、句读点被剔除的比例、墨迹损失率；
2. **OCR 探针**：随机 200–500 字（人工核对），**按大字/小字分层各测一组**，测准确率。
   **准确率只作参考**（由所有者/第三方核，或按 §4.1b 单册标定估）；
   真正的闸门是 §8 的"引文匹配后不一致率 ≤ 5%"；
3. **字号探针**：随机 30 页，量字头/注文的字面高度比，决定 §5.2 的分组策略。

#### 4.6 干净集必须**按页留出**（C 线没有参照文本，这是唯一正确做法）

A/B 用"全书只出现一次的字"当干净集，**因为它们有参照文本兜底**（B 的 629 个里 191 个来自
`ref_corrected`）。**C 没有参照文本，"单次字"= 只有一个 OCR 见证的字 = 全库最不可信的标签。**
拿它当测试集，指标会系统性偏低且不可解释。

正确做法：

1. 抽 **5–10% 的页**（约 180–350 页）完全不参与训练；
2. 干净集从**留出页上的多见证字**里取，一处一字；
3. `24_build_singles.py` 需新加 `--holdout-pages`，并断言：**训练页 ∩ 留出页 = ∅**。

这样既无泄漏，又只用可信标签。

#### 4.7 页面物理尺寸不统一 → 不能用固定 pitch

实测（§2 已列）：页面高度 **696 – 2946 pt** 都有，同一册内逐页不同；内嵌图 4,698–5,870 × 7,921–9,918。

**后果**：切字、字距、字号阈值都不能写常数，必须**按页各自的 pitch 反推**
（`estimate_pitch(lo, hi)` 的参数是 `lo/hi`，默认区间按四书的 300 dpi 页面定的，
C 线要按每页的实测 pitch 分布重新给区间）。A/B 两线都是靠固定 pitch 起家的，**这条是新的**。

#### 4.8 双行小注的切字（方案初稿完全漏了）

《永乐大典》的小字注文**常常是双行并排**（一行空间里塞两行小字）。
A/B 的切字器都假设"一行一字、单行垂直排列"，直接搬会**把双行注文切成半个字**。

Phase 0 必须量：(a) 双行注文占多少页；(b) 双行区的行宽是不是单行的 1/2。
若是，切字时按列内投影的**峰数**判定单行/双行，双行区按横向再一分为二。

### 5. 多抄手、双字号、篆书 —— 三个必须显式处理的变量

#### 5.1 多抄手（嘉靖录副由百余人分抄）

这是**风格问题不是标签问题**。三种做法，按推荐度排序：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐先做）** | 单模型，全量混合训练；**记录每页的"抄手聚类"** 作为元数据，评估时按簇报告指标 | 最省事；若簇间差异大，指标会露出来 |
| B | 先对页面做风格聚类（笔画宽度分布、字面宽高比、横画倾角），挑主导簇训练 | 需先做聚类，多一周 |
| C | 每簇一个模型，发布时按簇混合 | 最贵，等 A 的指标证明有必要再说 |

**判据**：如果按簇报告的 chamfer 差异 < 10%，单模型就够，不必分抄手。

#### 5.2 双字号（大字字头 vs 小字注文）

**不要一上来就分开训练。** 先做这一步：

1. 切字时给每格记 `size_class`（大 / 小），按列内的字面高度中位数判定；
2. 归一化会把两者都缩到同一个 em 框，**但小字的笔画相对更粗、细节更少**（A 线 E37 的同型问题）；
3. 训练时**先混合**，评估时**分开报告** Dice / chamfer / 墨量比；
   **Phase 0 必须先量大小格的格数比**——若小字占 80%，模型会整体偏向小字的笔性，
   那时"混合"就不再是中性选择（A 线 E39 的教训）；
4. 若两类指标差 > 15%，再考虑分开训练或按类加权（`--weight-complexity` 的同类思路，见 E39）。

**这一条有前车之鉴**：A 线 E39 证明"按复杂度加权"能改善复杂字，但也把 728 个字画坏；
E40 用混合检查点才收回来。**先把两类分开度量，再决定要不要分开训练。**

#### 5.2b 异体字与码位政策（必须先定，否则覆盖会悄悄缺口）

《永乐大典》俗字极多，OCR 会给出基本区之外的码位（含兼容汉字、扩展区、异体）。
发布字体只承诺 CJK 基本区 20,992，所以要在标签阶段就定好：

1. 先按 **Unihan 变体映射**（`kSemanticVariant`/`kSimplifiedVariant`/`kTraditionalVariant`）。
   **注意：`data/ids/` 里只有 `ids.txt` 与 `Unihan_IRGSources.txt`，没有变体字段**——
   需要另外下载 `Unihan_Variants.txt`，或直接用 **OpenCC** 做繁简/异体归一；
   把异体/俗字映射回基本区码位；
2. 映射不了的**直接丢弃并计数**，写进 `docs/DATA-C.md`；
3. 报告最终覆盖率时同时报"因码位政策丢弃了多少格"，否则覆盖率会看起来莫名其妙地低。

#### 5.3 篆书 / 隶书

- 版面里出现的篆形、隶形字头（常见的标记词：`篆`、`隸`、`六書`、`統`）；
- **先量再决定**：Phase 0 统计篆/隶格到底有多少。若只是每册卷首 1–2 个大字头，
  **版面规则就够了**（页首 + 大字 + OCR 命中「篆/隸/六書/統」），200 格人工标注纯属浪费；
  只有当出现率 >1% 且分布散乱时，才值得训分类器；
- 判据：篆/隶格一律**不进真迹集、不进训练集**，只在最终统计里报告剔除了多少。

### 8. 分阶段计划（每阶段都有明确的停止条件）

**Phase 0 · 普查（1 天）**
**第 1 步**：每册抽 **3 页（首页 + 2 页随机正文页，页面尺寸随册变化，只抽首页会看偏）**，量：
页面平整度、红线覆盖率（竖线条数）、**每页 pitch 分布**、**大小字格数比**、**双行注文比例**、
破损/污渍格占比、篆隶格占比。
**停止条件**：任一项异常到无法处理就回来报告，不要闷头往下做。

**Phase 1 · 试点（3–4 天）**
选 **3 册**（建议 卷10934 楚字、卷11618 老字、卷14131 第字，风格差异大）跑通全链路，
产出 500–1,000 个真迹字的小字体。
**停止条件（硬闸，任一不达标就停，不许带病进 Phase 2）**：

> **关于"人工核"的说明**：执行本任务的 AI 会话**无法自己"人工核"明抄本楷书**——
> 它只能拿另一个模型当判据，而那就是被测对象本身。所以：
> **主闸用可自动复现的代理指标（引文匹配后不一致率），人工抽检只作为抽查，且必须由所有者
> 本人或所有者指定的第三方执行。** 抽样清单格式：`页码 + 格坐标(行,列) + 裁切图路径 + 我们的标签`，
> 交给人逐条判对错。

| 闸门 | 阈值 |
|---|---|
| **引文匹配后不一致率（主闸，可自动复现）** | **≤ 5%**（能匹配上公版古籍的段落，对齐后的逐字不一致率） |
| 引文命中率 | ≥ 20%（低于此说明古籍库覆盖不够，"自动闸"不成立，转人工闸） |
| **silver 集错字率**（人工抽检，**由所有者本人或指定第三方核**） | **≤ 2%**（200–500 格，含形近字专项） |
| 训练页 ∩ 留出页 | = ∅ |

**Phase 2 · 全量（1–2 周）**
41 册全跑，切字 → OCR → 多见证 → 选优 → 训练 80 轮 → 全量生成。
预计真迹字数 **3,000–6,000**（B 线 4,078，覆盖 19.4%）。

**Phase 3 · 发版**
按 AGENTS 的发布流程，产出 `GuanGeKai-C-v1.0.0.zip`。

### 11. 并发与时间预算

- **同时最多 10 线程 / 20 核**（所有者明令）。多进程脚本三件套：
  `torch.set_num_threads(1)`、`cv2.setNumThreads(1)`、`OMP/MKL/OPENBLAS_NUM_THREADS=1`；
  `--workers ≤ 8`；启动后 `ps` 核对总 CPU ≤ 2000%。
- 粗估（**已按 B 线实测校准**）：抽图 3,538 页约 1 小时；**OCR 约 22 分钟**（B 线 1,613 页用 597 s，
  8 worker 线性外推）；切字约 2 小时；训练 80 轮约 4–5 小时；全量生成 25 分钟。
- **视觉聚类不用做全局两两**（70 万格 O(n²) 跑不动）：**先按 OCR 标签分组**（约 4–6 千组，
  每组约 140 格）→ 组内聚类得到该字的视觉变体（通常 2–5 个）→ 只比组间原型（5 千个原型、
  约 25M 对，秒级）。这样既避开 ANN，又正好对应 §4.3 的判据"同簇必须同标签"。
  **预算：半天写 + 半天跑全量。**
- 磁盘：3,538 页 300 dpi 抽图约 **30–50 GB**，加上切成 70 万格的 PNG 还要 10–20 GB。
  先确认 `work-c/` 所在盘有 **80 GB 以上**空间，并在 `docs/DATA-C.md` 记下清理策略。

### 13. 一句话总结

**A 线是写本、B 线是抄本，都有一份"标准答案"可以对齐；C 线是一份没有标准答案的类书。**

标准答案这条路已经查死：识典古籍最多收到卷 7,602，我们这 41 册是 6,831–19,792。
所以 C 线的全部难度集中在**标签体系**：

```
OCR（PP-OCRv6）
  + 视觉聚类（同簇必须一致）
  + 第二见证（换引擎/换预处理，错误模式要不相关）
  + 引文校正（能匹配上的公版古籍段落）
  → silver 标签，错字率 ≤ 2% 才许进训练
干净集：按【页】留出，绝不用"单次字"
```

**你的首要任务不是训模型，是让标签可信。模型侧直接抄 A/B 的配方（5 层 PatchGAN + hinge + 80 轮）。**
